# requirements

実装前に既存コードを調査し、要件定義書を書く。

要件は頭の中ではなくコードの中にある。既存実装を読まずに書いた要件定義は、実装段階で前提が崩れる。

## 手順

### 1. 前提を疑う

ユーザーの説明に出てくる固有名詞を、コード上の実体と突き合わせる。社内の呼び名とコード上の構造が一致している保証はない。

確認すること。

1. 登場するシステム・画面・エンティティが、コード上のどれに対応するか
2. 同じ名前で別の実体が複数ないか
3. 「管理画面」「業者向け」等の役割の呼び名が、認証主体と一致しているか

ここで食い違いを見つけたら、要件を書き始める前にユーザーへ提示して確認する。前提が違えば以降の全てが無駄になる。

### 2. チケット管理を見る

同じ話が既に起票されていないか探す。Jira / GitHub Issues / bd（beads）のうち、そのリポジトリで使われているものを見る。

1. 同じ機能のチケットが既にあるか
2. 親エピックに関連チケットが並んでいないか
3. 未マージ PR に前提となる実装がないか

チケットの本文がユーザーの説明と食い違うことがある。その場合は両方をユーザーに示す。

### 3. 既存実装を調査する

Explore サブエージェントを使う。調査項目を具体的に列挙し、ファイルパスと行番号付きで報告させる。

調査すべきこと。

1. 似た機能の既存実装。それが今回の雛形になるか
2. 作ろうとしているものが本当に存在しないか。部分的に存在しないか
3. 関連するモデルの構造と、それらの関連
4. 作成・更新の既存経路と、必須パラメータ、バリデーション
5. 付随して動くもの（決済・通知・ステータス遷移・バッチ）の実装状況
6. 同じ名前のカラムが別の意味で使われていないか

複数の観点を1つのサブエージェントにまとめて渡す。観点ごとに分けると調査が重複する。

### 4. 要件定義書を書く

以下の構成で書く。

```
1. 概要 — 何を作るか。現状何がないか
2. 現状 — 調査で分かった既存構造。ファイルパス:行番号 付き
3. 要件 — 機能要件、確定事項、設計方針、非機能要件
4. 実装範囲 — サーバ側、フロント側、範囲外
5. 前提となるブランチ — 未マージ PR に依存する場合
6. 未決事項 — 判断が必要なもの
7. 関連チケット
```

書き方の規則。

1. 主張には根拠のファイルパス:行番号 を付ける。付けられない主張は調査不足
2. 「確定事項」と「未決事項」を分ける。ユーザーが決めたことと決めていないことを混ぜない
3. 範囲外を明示する。書かないと含まれていると読まれる
4. 決定に至った経緯は書かない。0ベースで書くならそう書かないものは書かない

### 5. 未決事項を絞る

自明なものを未決に上げない。実装先が決まれば自動的に決まることは未決ではない。

未決に残すのは以下だけ。

1. 複数の選択肢があり、どちらでも成立するもの
2. ユーザーの判断がないと決められないもの
3. 既存の挙動を変えるかどうか

### 6. crit にかける

要件定義書ができたら crit でレビューを受ける。

## 成果物の置き場所

リポジトリを汚さないよう、まずスクラッチパッドに書く。ユーザーがリポジトリ内に置きたいと言った場合のみ移す。

## やってはいけないこと

1. 調査せずに要件を書く。既存実装の構造を知らずに書いた設計は成立しない
2. ユーザーが言っていない前提を足す。実装先が決まっているなら、そこから決まることを未決に上げない
3. 用語をコードで確認せずに使う。社内の呼び名とコード上の名前は一致しないことがある
4. 工数を要件定義書に混ぜる。見積もりは estimate スキルの仕事
