# estimate

要件から工数を見積もり、実装可能な単位のタスクに分割する。

分割していない見積もりは当たらない。全体を眺めて出した数字と、タスクに割って積み上げた数字は必ずずれる。ずれる方向は常に過小。

## 手順

### 1. 入力を確認する

要件定義書があればそれを読む。なければ requirements スキルで先に要件を固める。

要件が固まっていない状態で見積もると、前提が変わるたびに数字が動く。

### 2. 既存実装の再利用度を測る

見積もりの精度は、どれだけ既存を流用できるかで決まる。

確認すること。

1. 雛形になる既存実装があるか。あるならどの程度そのまま使えるか
2. 流用先が引数や前提に依存していないか（`current_user` 依存など）
3. 作成後に動くもの（決済・通知・遷移）が既に完成しているか
4. 未マージ PR に依存していないか

流用できるものが多いほど工数は下がる。ただし「流用できるはず」と「流用できる」は違う。実際にコードを読んで確認する。

### 3. タスクに分割する

1タスク 1〜3人日にする。3人日を超えるものはさらに割る。

分割の軸。

1. レイヤーで割る（DB、モデル、API、フロント）
2. 登場人物で割る（作る側、受け取る側）
3. フェーズで割る（基盤、API、通知、フロント、検証）

各タスクに書くこと。

1. 工数（人日）
2. 対象ファイル。新規か既存か
3. 完了条件。テストを含む
4. 依存するタスク
5. 前提（未マージ PR、未決事項の結論）

### 4. 依存関係を図にする

どのタスクが並行できるか分かる形にする。

```
T01 ─┬─ T02 ─── T03
     └─ T04
```

前提が揃わないタスク（未マージ PR 待ちなど）を明示する。

### 5. 分割で見えたものを反映する

分割すると、要件段階では見えなかった作業が出てくる。

よく出てくるもの。

1. マスタ取得 API。何かを選ばせるなら選択肢を返す口が要る
2. 一覧・詳細・取消。作る機能だけでは運用が回らない
3. 計算の共通化。2箇所で同じ値を出すなら食い違わない作りが要る
4. E2E とリグレッション確認

これらが出た結果、要件段階の見積もりより増えることがある。増えたことと、なぜ増えたかを明示する。隠して辻褄を合わせない。

### 6. 削る候補を示す

合計を出したら、削れるタスクとその影響を示す。

「29人日です」だけでは判断できない。「T07 の2人日は業者が下書きを追えなくてよいなら落とせます」まで書く。

### 7. 並行実施の想定を出す

人数を仮定して実日数を出す。依存関係から自動的に決まる。

## 見積もりの規則

1. 幅で出す。単一の数字は嘘になる
2. テストを工数に含める。含めない見積もりは必ず外れる
3. 「調査」を独立したタスクにしない。調査は各タスクに含まれる
4. レビューと修正の往復を見込む。見込まないなら、見込んでいないと明示する
5. 範囲外を数字から除く。除いたことを明示する

## やってはいけないこと

1. 分割せずに総額だけ出す。当たらない
2. 分割後に数字が増えたのを隠す。増えた理由を書く
3. 前提が固まっていないまま見積もる。未決事項があるなら、どの未決がどのタスクの工数を動かすか書く
4. 楽観と悲観を混ぜる。流用できる前提で下限、できない前提で上限を出す
