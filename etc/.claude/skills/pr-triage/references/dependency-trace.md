# 共用ファイルの依存関係調査

パス一致で切れなくなった段階で使う。共用ディレクトリにあるファイルが、対象機能から到達するのか、他からしか使われないのかを、コードを読んで判定する。

## 進め方

残ったPRが触るファイルを変更頻度（そのファイルを変更したPR数）で並べ、上位から subagent に追わせる。頻度が高いものほど、除外できたときの効果が大きい。

```bash
python3 <skill>/scripts/filter.py --show-dirs --depth 5 --top 30
```

## subagent への指示に必ず含めるもの

**対象機能の入口を具体的に書く。** フロントのディレクトリ、APIの名前空間、コントローラの基底クラス名。これがないと何を「到達」と呼ぶか判断できない。

**対比する名前空間も列挙する。** ユーザー向け、管理画面、外部連携、公開サイト。それぞれのコントローラ命名規則を書く。

**判定分類を定義する。** 到達する / 他からしか使われない / バッチ専用 / デッドコード。

**方法を指定する。**

- ファイルを実際に読むこと。grep の参照グラフだけで判断しないこと
- クラス名(CamelCase)とファイル名(snake_case)の両方で grep すること
- 呼び出し元を1段ずつ上へ辿り、コントローラ・rakeタスク・バッチ定義・ジョブに行き着くまで遡ること
- ルーティング定義でパスを裏取りすること
- フロント側が実際にそのエンドポイントを呼んでいるかも確認すること
- 推測で埋めないこと。参照が見つからなければ「参照なし」と明記すること

**出力形式を指定する。** ファイルごとに「役割 / 呼び出しツリー(パス:行番号) / 判定 / 根拠」。最後に判定別のグループ分け要約。

## 指示テンプレート

```
<repo> の <言語/フレームワーク> で、共用と思われるファイル群が
対象機能 <対象> から到達可能かを判定してほしい。

背景:
- 対象機能のフロントは <パス>、裏側APIは <名前空間>（<基底クラス>を継承）
- ユーザー向けは <名前空間>、管理画面は <名前空間>、公開サイトは <名前空間>

作業パス: <絶対パス>
調査対象リスト: <ファイルパス>

各ファイルについて:
1. 実際に読んで役割を1行で要約（存在しなければ「存在しない」と明記）
2. クラス名とファイル名の両方で grep して参照元を洗う
3. 参照元を上へ辿り controller / rake / バッチ / ジョブ に到達するまで遡る
4. 到達した controller の名前空間を判定（ルーティング定義で裏取り）

判定:
- REACHABLE / MIXED: 対象から到達（残す）
- OTHER_ONLY: 他からしか使われない（除外候補）
- BATCH_ONLY: バッチ専用（除外候補）
- DEAD: 参照なし・ファイル不在（除外候補）

出力: ファイルごとに「役割 / 呼び出しツリー(パス:行番号) / 判定 / 根拠」。
最後に判定別のグループ分け要約を出し、除外可能なものを明確にリストすること。

推測禁止。読んで確認した事実のみ。grep で見つからなければ「参照なし」と明記。
```

## 結果の扱い

**subagent の結論は必ず自分で検証する。** 要となる判定（特に「除外できる」という結論）は実コードで確認する。

実例での誤り:

- あるサービスを「ユーザー側専用」と報告してきたが、実際には別のサービス経由で対象機能から呼ばれていた。呼び出し元を1段しか辿っていなかったのが原因
- 同じファイルについて2回の調査で結論が割れた。片方は「モデル層コールバック経由の間接到達」、もう片方は「直系パス」。実コードを見ると後者が正しかった

検証は3〜4個の grep で足りる。concern の include 元、それを使うモデルのメソッド、そのメソッドを呼ぶコントローラ、フロントがそのエンドポイントを叩いているか。

到達すると確認できたファイルは `keep_substrings` に入れる。機能名でまとめて除外しつつ例外だけ守れる。

## 判定が割れやすいもの

**設定値の生成物。** 生成された定数ファイルが対象機能から import されていれば、それは仕様変更の経路になる。生成元のタスクも同様。

**モデル層のコールバック。** コントローラから直接呼ばれていなくても、モデルの save フックから走るなら到達する。

**名前に対象機能の語を含むが無関係なもの。** 外部連携の名前空間下に同じ語のファイルがあることがある。名前だけで判断しない。
