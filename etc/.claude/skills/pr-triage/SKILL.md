大量のマージ済みPRから、特定機能に関係するものを漏れなく拾い、人間が判定できる形にする。

想定用途は、旧実装から新実装への移植漏れ検証、機能単位の棚卸し、リリース範囲の影響調査。

## 前提となる考え方

**機械は切り捨てをしない。** 絞り込みは「候補を消す」のではなく「明らかに無関係なものを除外し、残りを人間に見せる」。取りこぼしが最も高くつくので、判定は必ず人間が行う。

**基本はPRではなくファイル行を消す。** 1 PR を複数のファイル行として扱い、除外ルールに当たる行を削る。全行が消えた PR だけが母集合から落ちる。こうすると「無関係ファイルと対象ファイルを両方触った PR」が生き残る。「別プロジェクトも触ったから丸ごと除外」のような取りこぼしが構造的に起きない。

**移植先の新実装だけはPR単位で落とす。** 新アプリ向けAPIのように「それを含むPRは移植元ではない」と言い切れるものは `exclude_pr_if_touches` で PR ごと除外する。ファイル行方式だと、100ファイル中95ファイルが新実装でも残り5ファイルの数行でPRが生き残り、判定材料がその数行だけになって誤判定を招く。

**共用ディレクトリはパスで切れない。** 対象機能の裏側ロジックが全機能共用のディレクトリにある場合、パス一致では適合率も再現率も両立しない。この段階に来たら依存関係調査（後述）に切り替える。

## 手順

作業ディレクトリを1つ決めて、そこで全スクリプトを実行する。生成物が10個以上できるので、リポジトリ直下は避ける。

### 1. PR番号を取得する

```bash
python3 <skill>/scripts/fetch_numbers.py <owner/repo> <開始YYYY-MM> [終了YYYY-MM] [--base BRANCH]
```

マージ月ごとに分割して Search API を叩く。`gh pr list --search` は1000件で頭打ちして黙って切れるので使わない。

`--base` を付けるかは要件次第。「releaseにマージされたPR」なら `--base release`、「全部」なら省略する。**ここを勝手に絞ると後で母集合がずれる。** 迷ったら省略して全base取り、後で base 列で分ける。

出力: `pr_numbers.txt`

### 2. フルデータを取得する

```bash
python3 <skill>/scripts/fetch_prs.py <owner/repo>
```

GraphQL の alias で20件ずつ束ねて1リクエストにする。コミット・レビュー・変更ファイル・コメントまで取る。502が散発するのでリトライ内蔵。中断しても再実行で続きから走る。

出力: `prs.json`（1000件で30〜40MB程度）

**取得後に必ず件数を検証する。** `pr_numbers.txt` の行数と `prs.json` の件数が一致するか確認する。日付が変わると母集合も増えるので、期待値は GitHub 側で数え直す。

### 3. 除外ルールを重ねて絞る

`filter_config.json` を作る（雛形: `<skill>/assets/filter_config.example.json`）。

```bash
python3 <skill>/scripts/filter.py --show-dirs
```

残ったPRが触るディレクトリが頻度順に出るので、明らかに無関係なものを `exclude_prefixes` に足して再実行する。これを繰り返す。

除外を足す順番:

1. 別プロジェクト・別アプリのディレクトリ（モノレポなら他パッケージ）
2. テスト・設定・スクリプト・ドキュメント
3. メタファイル（CI設定、依存ロック、ドットファイル）
4. 対象機能と無関係な機能ディレクトリ（部分一致 `exclude_substrings` が効く）

**除外の可否は必ずユーザーに確認する。** 特に「一見関係なさそうだが実は対象機能から使われている」ものを機械が判断してはいけない。

設定項目:

| キー | 役割 |
|:---|:---|
| `confirm_prefixes` | 対象機能の本体。触ったPRは除外プロセス外の「読む対象確定」になる |
| `exclude_prefixes` | 前方一致で除外 |
| `exclude_substrings` | 部分一致で除外。名前空間が階層のあちこちに散る場合に使う |
| `exclude_pr_if_touches` | このパターンを1ファイルでも含むPRを丸ごと除外（PR単位） |
| `exclude_basenames` | ファイル名一致で除外 |
| `keep_substrings` | exclude より優先して残す。依存調査で到達を確認したファイルを守る |
| `specific_patterns` | 対象機能に固有のファイル。当たれば specific（読む対象確定）、外れれば shared（要判断） |
| `nondev_*` | 統合PR・リリース束を母集合から外す条件 |
| `body_cut_pattern` | PR本文のうちこの見出し以降を捨てる（テンプレートの定型部分） |
| `jira_pattern` / `jira_base` | Jira キー抽出とリンク生成 |

`nondev_*` で外すのは、中身が寄せ集めで、含まれる開発が個別PRとして別途母集合にいるから。残すと二重計上になる。実例では1372件中436件がこれに当たった。

### 4. 共用ファイルは依存関係で判定する

パス一致で切れなくなったら、残ったファイルを変更頻度順に並べ、subagent に呼び出しツリーを追わせる。

指示テンプレートと検証手順は `references/dependency-trace.md` に置いてある。共用ディレクトリの絞り込みに入る時に読む。

要点だけ挙げると、subagent には対象機能の入口（フロントのパス、APIの名前空間、基底クラス）を具体的に伝え、実際にファイルを読ませ、ルーティングで裏取りさせる。

**subagent の結論は必ず自分で検証する。** 実例では「ユーザー側専用」と報告されたファイルが、実際には別サービス経由で対象から到達していた。要となる判定は3〜4個の grep で確認できる。

到達すると確認できたファイルは `keep_substrings` に入れる。`exclude_substrings` より優先されるので、機能名でまとめて除外しつつ例外だけ守れる。

### 5. 判定UIを作る

```bash
python3 <skill>/scripts/build_review_data.py
python3 <skill>/scripts/fetch_diffs.py <owner/repo>
cp <skill>/assets/review.html .
nohup python3 -m http.server 8765 --bind 127.0.0.1 >| /tmp/pr-triage.log 2>&1 &
```

http://127.0.0.1:8765/review.html を開く。`fetch` を使うので file:// では動かない。

UIの仕様:

- `1`=対象 / `2`=対象外 / `3`=保留、`←→`=移動、`Enter`=次の未判定へ
- 判定は localStorage に自動保存。閉じても続きから再開できる
- 表示順は PR本文 → 変更ファイル一覧 → 差分
- 差分は判定対象ファイルのみ表示。除外済みファイルの差分はノイズなので出さない
- ファイル一覧は色分け（緑=対象機能の本体、青=判定対象として残った、薄字=除外済み）
- 右上「結果を書き出す」でCSVダウンロード

UIを直す時の注意:

- 判定ボタンはヘッダに固定する。カード内に置くと長い差分で画面外に消える
- スクロール領域を作らない。全文表示にしてページ全体でスクロールする
- PR本文は textarea 30行が読みやすい
- 差分のハイライトは patch 全体を一度だけエスケープしてから行頭記号で色付けする。1行ごとにエスケープ関数を呼ぶと数千行の差分で目に見えて遅くなる

### 6. 結果を出力する

feature でグループ分けしてスプレッドシートに書く場合:

```bash
python3 <skill>/scripts/build_sheet_rows.py --group confirmed --features features.json \
    --exclude <相殺するPR番号のカンマ区切り>
node --experimental-strip-types <skill>/scripts/write_sheet.ts <spreadsheetId> <シート名>
```

`features.json` の形式（例: `<skill>/assets/features.example.json`）:

```json
[
  ["行政申請・自治体連携", ["行政申請", "港区", "渋谷区", "利用券"]],
  ["リファラル・キャンペーン", ["リファラル", "キャンペーン", "MVP"]]
]
```

出力列は チケットID / JIRAリンク / GHリンク / チケットタイトル / 行数+ / 行数- 。
feature ごとにまとめ、各グループ内は変更行数の降順。

書き込みは対象シートをクリアしてから行う破壊的操作。**実行前に必ずユーザーの明示的な指示を得る。**

出力前に必ず除外すべきもの:

- **Revert で相殺するPR** — 実装PRとそのRevertは打ち消し合うので両方外す。ただし Revert of Revert は変更が復活しているので残す。時系列で追って最終形だけ残す
- **ブランチ同期のマージPR** — 「releaseをfeatureにマージ」のようなPRは仕様変更を含まず、中身は元PRとして母集合に既にある

スプレッドシートへの書き込みは `google-sheets` スキルを使う。

| `pr_numbers.txt` | PR番号（昇順） |
| `prs.json` | フルデータ |

## 落とし穴

**母集合を勝手に絞らない。** 「releaseにマージ」と言われて `--base release` で取った後、「全部」と言い直されたら取り直しになる。要件を確認してから取る。

**日付が変わると母集合が増える。** 数日またぐ作業では、最後にもう一度 GitHub 側の件数を数えて差分を取る。

**統合PR・リリース束が数字を膨らませる。** 「release to master」のようなPRは過去の全変更を含むので、対象ファイルを巻き込んで残る。母集合から外さないと件数が3割ほど水増しされる。

**generated ファイルは除外できないことがある。** 設定値の生成物（definitions.ts のような）が対象機能から import されていれば、それは仕様変更の経路になる。生成元の rake タスクも同様。
