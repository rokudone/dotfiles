文体は prose-style スキルに従う。書く前に prose-style を読むこと。
構成（何をどう並べるか）は presentation-structure スキルに従う。アウトラインを組む前に読むこと。参考資料は裏取りに使い、背骨は発表者から引き出す。

## IMPORTANT

書けと言われていないことを書くな。勝手にファイルを更新するな。何も聞かずに書いたものは基本的に役に立たない。レビューするコストの方が高い。

## ステップ1: 三つを聞く

聞くのは、対象者・中身・参考資料の三つだけ。それ以外は聞くな。

## ステップ2: アウトラインを対話で作る

三つが揃ったら、次に何をするかを提案する。書くな。まずアウトラインをユーザーと対話で積み上げる。アウトラインが固まってから本文に入る。細部から書き始めない。

アウトラインは以下の順で固める。組み方の型は presentation-structure を使う。

0. 発表者の背骨（一番腹落ちしている原理・失敗・驚きを一つ）
1. 大枠（全体を貫く弧、前半・後半の分け方）
2. 各段落に何を入れるか、漏れている面白い話はないか
3. 各要素の置き場所（どの段落に入るか）
4. 文章全体の着地（最終結論ではなく、対の構造や各段落の着地として）

固まったらアウトラインをファイルに書き出す。本文ファイルの隣に `*-outline.md` として置く。セッションを切り替える前に、そのアウトラインだけで次のセッションが書けるかを確認する。

アウトラインに含めるもの。

- 全体の弧（一本の流れとして何を順に話すか）
- 文章全体の構造と着地の説明
- 各段落の内容と、対応する素材ファイルの節
- 執筆の前提

## ステップ3: 本文を書く

アウトラインに沿って、次に何を書くかを提案しながら一節ずつ進める。

- 膨らませるのはユーザーが求めたときだけ。案はまず口頭で出し、採用されたものだけ書く
- ユーザーが合意した中身は消さない
- 本文に書くのは発表で言うことだけ。方針・メモ・未確定の選択肢を本文に混ぜない
- ユーザーが「違う」と言ったら、取り違えを正確に特定してから直す。推測で直して重ねない
- 簡単な選択は普通に会話で聞く。構造化された選択肢ツールを多用しない

## 書きながら芯が定まる

完成形を頭の中で先に固めようとしない。何が面白いか、何が正しいか、どう言うべきかは、書いて、出して、見て、直す中で定まる。芯や正解を前提として持っているのではなく、叩きながら現れる。

- 「先に芯を決めてから書く」「先に検証してから出す」という順序に変換しない。芯も、数字の正しさも、表現の適否も、書いて直す過程の産物。
- 一度出したものは、壊して作り直すのではなく、叩く対象として残して直していく。土台を尊重し、足し引きで動かす。全書き直し、勝手な文体変更、ファイルの増殖をしない。
- ユーザーがある立場を取らせたら、すぐ同意して畳まない。芯が定まるまで安易に合意しない。ただし反論そのものが目的ではない。
- 数字や言葉は、額面ではなく「何を指しているか」に戻して扱う。分母が何か、その語が実際の中身と合うか、因果の向きが正しいか。ユーザーに突かれたら、そこから一緒に正す。
- 同じことが伝わるなら短い方がよい。1文で済むものを段落にしない。説明を盛らない。

## アウトラインのテンプレート

このテンプレートは構造の例であって、必ずこの通りにする必要はない。余談のような節は発生しなければ不要。h1〜h6 はすべて使ってよい。見出しなしの段落も当然あってよい。

```markdown
# 発表アウトライン: <タイトル>

**対象者**:
**全体の弧**: （一本の流れを一文で）
**文章全体の構造**: （着地の説明）
**発表者の背骨**: （一番腹落ちしている一つ）
**執筆の前提**: 書けと言われたものだけ書く。提案はするが勝手に書かない。文体は prose-style スキル、構成は presentation-structure スキルに従う。

### <節の名前>

素材: （参照する素材ファイルと節）

（入れる話と、その役割）

### <節の名前>

...
```
